# InnoNetwork 6.1.0 encoded-request candidate

Status: Draft, unpublished. Implementation and validation are authorized; this
document is not Ready approval, a published version, or permission to tag.
The [older 6.1 scope record](6.1.0.md) describes a different roadmap that was
absorbed into 6.0. This candidate is subsequent work on the encoded-request
boundary, not a reversal of that historical scope decision.

## Candidate contents

- A public buffered `EncodedRequest` / `EncodedRequestClient` boundary for
  binary codecs, sharing admission, retries, cancellation and operation deadlines
  with JSON clients without requiring Codable or GeneratedClientSupport SPI.
- Named `EncodedAPIDefinition` endpoints, once-per-invocation payload encoding,
  explicit no-content response decoding and payload-free encoding failures.
- Compiler-host `InnoNetworkMacroSupport` for macro-first companions, with a
  separate twelve-declaration, minor-bound contract. The Protobuf 6.0 candidate
  uses this boundary; it does not add another transport or retry implementation.
- Macro declaration admission and identifier fixes; response-cap-aware
  coalescing; corrected non-S3 canonical paths; bounded numeric recovery for
  persistent cache and download logs; signed-attempt interceptor provenance.
- Persistent-cache telemetry aggregated by reason between drains, with
  saturating totals and an explicit single-active-owner directory contract.

See [Unreleased changes](../../CHANGELOG.md),
[API classifications](../../API_STABILITY.md), and
[migration notes](../Migration-EncodedRequests.md) for the exact contracts.
Exhaustive error switches and previously accepted conditional macro members may
need source changes; this candidate is not advertised as universally source
compatible. Multi-process cache locking is not implemented.

## Validation and publication gates

[Remediation evidence](../REMEDIATION_2026_09_30.md) records the prior review and
its corrected DocC gate. [Pre-release hardening evidence](../PRE_RELEASE_HARDENING_2026_09_30.md)
records the subsequent telemetry and physical-app validation against the new
sources. Fresh results and reused evidence are identified separately.

- [ ] Exact final-candidate remote CI, including both supported toolchains,
  required checks, performance and full ThreadSanitizer validation.
- [ ] Maintainer review of source-compatibility changes and candidate release
  version, followed by protected main integration and final-main validation.
- [ ] Candidate-specific Ready approval, version/tag consistency and explicit
  publication authorization. A successful legacy `6.0-release-state` check
  verifies the historical 6.0 contract; it is not approval of this candidate.
- [ ] After core publication, Protobuf resolves the public core dependency with
  no local override and completes its own final-main/release gates.

Loopback execution on a physical iPhone is real URLSession and sandbox-file
evidence, not certification of external TLS/pinning, OS background restoration,
locked-device behavior or dedicated IdP/exporter/AWS/FairPlay integrations.
Application-specific adoption checks remain required for those capabilities.
