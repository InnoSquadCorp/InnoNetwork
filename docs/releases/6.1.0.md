# InnoNetwork 6.1.0 encoded-request candidate

Status: Draft, unpublished. Implementation and validation are authorized; this
document is not Ready approval, a published version, or permission to tag.
The selected next release version is `6.1.0`. Preparation continues on top of
the merged encoded-request baseline; the first-line Draft marker stays in place
until the final candidate and publication decision are explicitly approved.
The [older 6.1 scope record](archive/6.1.0-superseded-roadmap.md) describes a different roadmap that was
absorbed into 6.0. This candidate is subsequent work on the encoded-request
boundary, not a reversal of that historical scope decision.

## Candidate contents

- A public buffered `EncodedRequest` / `EncodedRequestClient` boundary for
  binary codecs, sharing admission, retries, cancellation and operation deadlines
  with JSON clients without requiring Codable or GeneratedClientSupport SPI.
- Named `EncodedAPIDefinition` endpoints, once-per-invocation payload encoding,
  explicit no-content response decoding and payload-free encoding failures.
- Compiler-host `InnoNetworkMacroSupport` for macro-first companions, with a
  separate twelve-declaration, minor-bound contract. The Protobuf 6.0 candidate
  uses this boundary; it does not add another transport or retry implementation.
- Stable JSON macro conditional-source compatibility, explicit legacy-payload
  warnings and stricter admission for new encoded companion macros; identifier
  fixes; response-cap-aware
  coalescing; corrected non-S3 canonical paths; bounded numeric recovery for
  persistent cache and download logs; signed-attempt interceptor provenance.
- Persistent-cache telemetry aggregated by reason between drains, with
  saturating totals and an explicit single-active-owner directory contract.
- Bounded, cancellation-safe timer slices for large finite scheduling budgets
  in Core, WebSocket and restored downloads, without a new public total-wait cap.
  Finite retry jitter and cap-safe circuit backoff avoid fatal numeric conversion.
- Direct companion macro analysis tests, strict local Periphery parity with CI,
  and offline checks of current post-publication adoption guidance.
- Metadata-only CI rejects an authoritative main advance even when the PR API
  still returns the previous base. Native aggregate checks and the legacy
  validation inventory are audited separately without changing branch settings
  or relaxing the strict protection required for autonomous bot merging.
- Direct no-content status/body regression cases and an encoded 401-refresh
  replay case covering once-only encoding, identical replay bytes, updated
  authorization and final-response-only decoding.

## Dependency migration

Compared with the published 6.0.0 manifest, SwiftSyntax changes from
`603.0.1..<603.1.0` to `604.0.0..<604.1.0`, and Swift Crypto changes from
`4.0.0..<5.0.0` to `5.0.0..<6.0.0`. Swift tools 6.2 and the five Apple
deployment floors remain unchanged. An application graph that also requires
SwiftSyntax 603-only or Crypto 4-only cannot resolve this candidate. Disabling
the `Macros` trait avoids compiling macro products but does not remove manifest
dependency resolution. Review and align the whole consumer graph rather than
widening ranges without validation. See the
[dependency integration evidence](../DependencyIntegration-2026-10-02.md) and
[migration guide](../Migration-EncodedRequests.md#dependency-graph-compatibility).

Companion releases are separate. Their earlier paired CI does not certify this
Core graph. Core-only publication need not wait for optional companion release
work; adopting a companion requires its own compatible manifest, clean tagged
resolution and exact-pair validation.

See [Unreleased changes](../../CHANGELOG.md),
[API classifications](../../API_STABILITY.md), and
[migration notes](../Migration-EncodedRequests.md) for the exact contracts.
Stable JSON macro helpers and policies keep compiling with their 6.0 generated
contract. Conditional payload inference remains unsupported and now warns;
use a whole-endpoint conditional or an unconditional manual payload pair.
Provisionally Stable migrations include exhaustive configuration-error switches,
generic JSON operation wrappers (`where Base: NetworkClient`) and aggregated
cache telemetry. These require the explicit migration notes above, not a new
major release. Multi-process cache locking is not implemented.
